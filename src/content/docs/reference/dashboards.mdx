Dashboards are CLI tooling. They are YAML files of WireLog queries rendered locally or exported as HTML. WireLog remains headless and API-first.

## Commands

```bash
wl dashboard init --output dashboard.yaml
wl dashboard init --output -
wl dashboard schema --output -
wl dashboard validate --file dashboard.yaml
wl dashboard validate --file - --json
wl dashboard run --file dashboard.yaml --json
wl dashboard run --file dashboard.yaml --var range=7d --format markdown
wl dashboard view --file dashboard.yaml --open
wl dashboard view --file ./dashboards
wl dashboard save --file dashboard.yaml --output index.html --mode report
wl dashboard save --file dashboard.yaml --output - --mode report
wl dashboard save --file dashboard.yaml --output index.html --mode interactive --token-env WIRELOG_DASHBOARD_TOKEN
```

`wl dashboard run` executes every non-Markdown card query in one dashboard file and prints structured results.

`wl dashboard view --file <dir>` discovers `.yaml` and `.yml` dashboards under that directory and renders a sidebar for switching dashboards.
Each dashboard also has a stable local route, such as `/dashboard/usage.yaml`; extensionless routes like `/dashboard/usage` work when unambiguous.

## Export modes

- `report`: fixed data, no token embedded.
- `interactive`: embeds a query-scoped `aat_` token and lets browser controls re-run `/query`.

Interactive exports reject `pk_`, `sk_`, and `ak_`.
Team members should use their own personal query token, not a shared `sk_`.
When written to a file, interactive exports use `0600` permissions because the HTML contains the token.

## Creating dashboards with agents

- Start with discovery:
  - `wl query "inspect * | last 30d" --json`
  - `wl query "* | last 30d | count by event_type | top 20" --json`
- Use `wl dashboard schema --output -` when generating YAML.
- Validate before viewing or exporting.
- Test representative card queries with `wl query "..." --json` while authoring. Verify sources, filters, fields, rows, columns, and values match the card intent before trusting the YAML.
- Run the dashboard as data with `wl dashboard run --file dashboard.yaml --json`; fix unexpected zeros, empty rows, missing columns, or wrong modes before viewing/exporting.
- Use root `order` values like `10`, `20`, `30` for dashboard directories.
- Use root `timezone` to localize time display.
- Use the built-in `range` date-range control for time windows; use shared variables for segments.
- Use explicit chart options when columns are ambiguous.

## YAML

```yaml
version: 1
title: Product Growth
order: 10
refresh: 60s
timezone: UTC

variables:
  range:
    label: Range
    type: date_range
    default: 30d
  platform:
    label: Platform
    type: select
    default: all
    options:
      - label: All
        value: all
        fragment: ""
      - label: Web
        value: web
        fragment: '| where _platform = "web"'

sections:
  - title: Acquisition
    cards:
      - id: acquisition-trends
        title: Acquisition Trends
        kind: chart
        viz: line
        layout: {w: 8, h: 4}
        queries:
          - name: Signups
            query: signup {{range.stage}} {{platform.fragment}} | count by day
          - name: Activations
            query: activate {{range.stage}} {{platform.fragment}} | count by day
```

Variables are dashboard-level anchors. Dashboards automatically get a `range` date-range control unless they define their own `variables.range`. Use `{{range.stage}}` for a full time stage such as `| last 30d` or `| from 2026-04-01 to 2026-05-01`; old `| last {{range}}` templates still work for preset/custom values. Cards can also opt in with `{{platform.fragment}}` or safe input fragments.

Cards define either `query` or `queries`, not both. Use `queries` for overlays and explicit comparisons.

## Directory ordering

- `order: 10` controls sidebar order in `wl dashboard view --file ./dashboards`.
- Dashboards with `order > 0` appear first, sorted ascending.
- Dashboards without `order` sort by filename after ordered dashboards.
- Leave gaps so agents can insert dashboards later.
- Direct URLs use `/dashboard/<id>`, where `<id>` is the relative file path from the dashboard directory.

## Variables

Select variables use whitelisted values. Fragments are author-controlled YAML, not viewer text:

```yaml
variables:
  platform:
    label: Platform
    type: select
    default: all
    options:
      - label: All
        value: all
        fragment: ""
      - label: Web
        value: web
        fragment: '| where _platform = "web"'
```

Dynamic dropdown variables can load options from WireLog data. Static options are preserved first; dynamic options are sorted by ASCII value:

```yaml
variables:
  country:
    label: Country
    type: select
    default: all
    options:
      - label: All
        value: all
        fragment: ""
    query: '* | last 30d | count by _country | top 25'
    value_column: _country
    label_column: _country
    fragment_template: '| where _country = "{{value}}"'
```

Input variables are submit-only. Use them for user lookup dashboards with safe named fragments:

```yaml
variables:
  subject:
    label: User
    type: input
    input: email
    required: true
    submit: true
    placeholder: "email or *@example.com"
    allow_domain_wildcard: true
    fragments:
      events:
        exact_field: user.email
        domain_field: user.email_domain
      users:
        exact_field: email
        domain_field: email_domain
```

Exact emails become equality filters. `*@example.com` becomes a domain equality filter when `allow_domain_wildcard` is true.

```yaml
query: '* {{subject.events_fragment}} {{range.stage}} | list | limit 100'
query: 'users {{subject.users_fragment}} | list'
```

## Cards

Supported card kinds:

- `metric`
- `chart`
- `table`
- `events`
- `funnel`
- `retention`
- `journey`
- `sessions`
- `lifecycle`
- `stickiness`
- `users`
- `inspect`
- `markdown`

Supported visualizations:

- `number`
- `line`
- `area`
- `bar`
- `pie`
- `table`
- `event-stream`
- `funnel`
- `retention-grid`
- `path`
- `lifecycle`
- `histogram`
- `json`
- `markdown`

Chart cards can pin column bindings when inference would be ambiguous:

```yaml
options: {x: day, y: value, series: _browser}
query: 'page_view {{range.stage}} | count by day, _browser | top 50'
```

Line, area, and bar charts render time bucket columns (`hour`, `day`, `week`, `month`, date/time fields) on chronological axes. Multi-series time charts are aligned to one shared bucket domain; missing buckets render as gaps instead of lines connecting across absent data. Line and area charts keep the active time bucket live, draw the final segment as dashed, and mark its tooltip `partial` so current data stays visible without implying a complete-period comparison. For grouped time queries, set `options.x`, `options.y`, and `options.series` explicitly when the result has more than one non-metric column.

Local and interactive dashboards progressively load visible cards in layout order. They coalesce up to eight cards into one request, deduplicate identical rendered queries across the batch, and run at most eight query jobs concurrently. Cards entering the viewport settle for 400 ms. Query rate limits are surfaced immediately instead of being hidden behind automatic retry sleeps.

Dashboard-side ratios divide the first query by the second query:

```yaml
options: {calculate: ratio, x: day, y: value}
queries:
  - name: Purchases
    query: purchase {{range.stage}} | count by day
  - name: Signups
    query: signup {{range.stage}} | count by day
```
